02

The three jobs

Three jobs, one session

  • Code it. You have already done this by hand.
  • Make the machine code it. Same pages, same codebook.
  • Compare, then chart. Your rows become a figure and a Word file.

You are not learning to use AI today. You are learning to check it — and the only way to check a machine is to have done the work yourself first, which you have.

03

Which tool for which job

Two tools, and one to avoid

Both are on the LITS AI tools page and both take your Hamilton credentials. Pick one and work in it.

  • Amplify — amplify.hamilton.edu — Hamilton-hosted, with several models to choose from. It does not run Python.
  • Gemini — gemini.google.com — Google's model. It can run Python internally, which is how it counts and charts.
  • Adobe Firefly — not for charts. It draws pictures. It will happily draw something that looks like a bar chart, with numbers it invented.

The Firefly warning is the one to remember. An image generator has no idea what your data says — it produces a plausible picture of a chart, with numbers it invented. Never reach for one when you are asked to make a figure.

NotebookLM is worth knowing about too. It is genuinely good for asking questions of the roll — which entries mention a church? — but not for coding, because it answers in prose and will not give you a table you can trust row by row.

04

Set up, four steps

Before you prompt anything

  • 1. Open either amplify.hamilton.edu or gemini.google.com and sign in with your Hamilton account.
  • 2. Start a new conversation.
  • 3. Upload your roll PDF only — one roll, not the whole volume.
  • 4. Paste the coding prompt.

The point of a new conversation is to start the model with as little extra information or context as possible. It is not a clean slate. Depending on the tool and its settings, a model may still draw on your earlier chats or files, and no setting removes what it absorbed in training — Sharpe's edition has been online for years. A name the model "knows" looks exactly like a name it read. The only check is the page.

Step 4 matters for a duller reason: small talk before the prompt changes what the model does with the prompt. Paste it cold.

05

What a PDF is

First, what is a PDF?

A PDF records what a page looks like, not what the document is. A Word file knows this is a sentence, this is a paragraph, this is a heading. A PDF mostly stores draw this character, at this spot, in this font.

And a PDF can be made in three different ways.

Kind of PDFWhat is insideWhat you get when you extract the text
Exported from a word processorThe characters and where each one sitsThe text, almost exactly
A plain scanA picture of each page, nothing elseNothing
A scan plus OCRThe picture, with an invisible layer of machine-guessed text laid over itThe guess

Ours is the third kind. What you see on screen is a photograph of a 1913 book; what a tool pulls out of the file is a machine's guess at it. Slide 7 shows how we know.

PDF stands for Portable Document Format. "Portable" means it is built to look the same on any screen or printer — which is exactly why it stores where each character goes rather than what the text means.

OCR stands for optical character recognition: software that looks at a picture of text and guesses which character each shape is.

06

Three ways in

A PDF can be read three different ways

  • Embedded text layer. The characters are already stored in the file. Instant, free, exact — if the PDF was made from a word processor. Needs no program to run.
  • The tool runs its own OCR — optical character recognition. Used when there is no text layer. A machine cuts the page into letter-sized pieces and guesses each one from its pixels. Needs to run a program.
  • The model looks at the page. A multimodal model treats the page as an image and reads it the way you would. Needs no program to run.

Nothing in the answer tells you which one happened.

The last line is the one that matters. The chat window hands you text whichever route the tool took, with no label saying where it came from. Everything else today follows from that.

07

The twist in our PDF

Our "text layer" is not text. It is OCR from December 2011.

The file says so itself. Ask it, with pdfinfo:

Creator:      Digitized by the Internet Archive
Producer:     Recoded by LuraDocument PDF v2.28
CreationDate: Mon Dec  5 01:20:43 2011 EST
ModDate:      Mon Dec  5 02:32:45 2011 EST
  • Created at 01:20, finished at 02:32 — 72 minutes of machine processing on a 366-page book.
  • pdffonts reports one font, Courier: not embedded, no character map. That is the signature of an invisible layer laid over a picture, not of typed text.
  • pdfimages reports every page as a 400 ppi image with a one-bit black-and-white mask over it. That mask is what the OCR read.
  • Note what the metadata does not say: which program read the letters. LuraDocument is the compressor. The engine is not named anywhere in the file.

Extracting the text layer does not get you Sharpe's edition. It gets you a fifteen-year-old machine's guess at it.

The chain between the clerk and you has four links, and every one of them can introduce error: the clerk's roll, Sharpe's 1913 translation, a 2011 scan, a 2011 OCR pass. The AI is the fifth link. You are the sixth.

How we know: pdffonts and pdfimages, two command-line tools, report the fonts and images inside a PDF in about a second.

What breaks, and where

The fields you need sit in the worst type on the page

FieldWhere it physically sitsWhat the text layer gives
WardOuter margin, small italicNfiii^aif · Crupiil^^aie · iVaiebroke · ^^''^^^

The pattern is the point. The fields you have to code do not live in the body prose. They live in the margins, the footnotes, the isolated numerals and the abbreviated money — the parts set in the smallest and most awkward type. A page can be 97% character-accurate and still have an unreadable ward.

One counter-intuitive detail: the money fails on cleanly printed pages. It is not faint ink. It is italic fractions. The failure is typographic, not a question of damage — which is the opposite of what you would assume about a scan of a 1913 book.

09

Find out how yours read it

You cannot tell from the answer. So test it.

With your roll uploaded, before anything else, send these two messages.

Diagnostic — message 1
How did you read the PDF I just uploaded? Answer in one sentence, and say specifically whether you extracted an embedded text layer, ran your own OCR on the page images, or looked at the page images directly. If you are not sure, say you are not sure.
Diagnostic — message 2
List the headings of entries 1 to 5 in this roll, exactly as they appear, character for character. Do not add or remove spaces, and do not correct spelling. If a heading is unclear, write it as you see it.

Every heading in the volume reads On the death of [name]. The stored text layer joins the of to the name, and it does it in every roll — ofJohn, ofCristina, ofElena, ofGerardle Friiyter. At least one of your first five entries will have it.

So: if the headings come back joined, the tool is reading the text layer and reporting it honestly. If all five come back with a clean space after of, it either looked at the page images or it tidied the text without telling you — and the second of those is the thing this whole session is about.

The tell is a single space. That is how small a quiet failure can be.

Do this first Run both messages before you paste the coding prompt, and note which of the two outcomes you got.
10

What a good prompt carries

Five things, or it will improvise

  • The exact columns, named and in order.
  • The value lists, closed, with an explicit option for "not stated".
  • The decision rules for the traps you already know about.
  • Evidence. A quoted phrase and a page number for every row.
  • A file, not a chat table.

This is prompt design, not prompt tricks. Every item on the list is there because leaving it out produced a specific failure. No closed list and you get 104 spellings of the ward. No "not stated" option and the model invents a relationship rather than leaving a blank. No evidence quote and you cannot settle a disagreement without reopening the page.

11

The prompt

Fill in two blanks at the top. Paste the whole thing.

Change ROLL_LETTER and CODER_ID and nothing else. If you edit the columns, your rows stop lining up with everyone else's and the class dataset breaks.

Type these once and they fill in below. Use student for your own coding, or the tool's name — gemini, claude, amplify.
Coding prompt — paste in after uploading the roll
ROLL_LETTER = {{ROLL_LETTER}}
CODER_ID    = {{CODER_ID}}

You are helping code medieval coroners' inquests into a dataset. The PDF I uploaded is one roll from R. R. Sharpe, ed., Calendar of Coroners Rolls of the City of London, A.D. 1300-1378 (1913).

Produce ONE ROW PER NUMBERED ENTRY, in printed order, with these 21 columns in exactly this order:

coder_id, roll, case_number, printed_page, entry_type, inquest_date, date_verbatim, ward, ward_verbatim, within_without, parish_verbatim, victim_name, victim_gender, victim_status, manner_of_death, weapon, weapon_verbatim, perpetrator_name, perpetrator_outcome, chattels_verbatim, evidence_quote

VALUES

entry_type: homicide | accident | death in custody | suicide | cause undetermined | no death recorded
manner_of_death: natural | accident | assault | suicide | undetermined | none
victim_gender: male | female | not given
victim_status: gentleman/woman | craftsman/woman | servant/labourer | apprentice | prisoner | destitute | cleric/religious | unknown
weapon: bare hands | knife/dagger | club/staff | axe | sword | bow and arrow | stone or thrown object | other | no weapon
perpetrator_outcome: captured | surrendered | abjured the realm | took sanctuary then escaped | fled, never taken | jury found no felony | perpetrator died | outlawed | not stated | no perpetrator
within_without: within | without | not specified | not applicable

RULES

1. coder_id and roll are the same in every row: the two values given at the top. coder_id names who or what did the coding — student, gemini, claude, amplify.
2. entry_type says what kind of RECORD this is. manner_of_death says how the person died. They are not the same question: an entry can be "no death recorded", and then manner_of_death is "none".
3. "lay dead of a death OTHER THAN his rightful death" = an UNNATURAL death. "DIED his rightful death" = a NATURAL death. These mean opposite things. Read the phrase carefully before coding manner_of_death.
4. Take the ward from the SENTENCE that names it, never from the marginal note. Put the raw spelling in ward_verbatim, modernised in ward.
5. inquest_date is the date at the head of the entry. That is when the body was viewed, NOT necessarily when the person died. Write it as M/YYYY.
6. date_verbatim: the date exactly as the entry gives it, feast day and regnal year included — for example "Tuesday next after the Purification B.V.Mary [2 Feb.] the year aforesaid".
7. printed_page: the number printed at the top of the page. These are often mis-transcribed (lOI for 101, Ill for 111). If you cannot read it cleanly, write ILLEGIBLE rather than guessing.
8. The five _verbatim columns: copy what the page says, exactly as printed, including damaged characters. Do not tidy, modernise or correct.
9. Any value you cannot read, write exactly: ILLEGIBLE. Any value the entry does not state, write exactly: NOT STATED. Never infer, never fill a gap from context, never guess a name.
10. evidence_quote: 5 to 15 words from the entry supporting manner_of_death.

OUTPUT

Write the result to a CSV file I can download. Quote every field.
Filename: roll_{{ROLL_LETTER}}_{{CODER_ID}}.csv

If you cannot create a file, say so in one sentence before anything else, then print the rows in the chat as CSV inside a single code block, every field quoted, no commentary between rows. Do not give me a formatted table instead of a file without telling me.

Then, in the chat and not in the file, tell me:
- how many rows you produced
- which case_numbers you could not read
- which fields you most often had to mark ILLEGIBLE

Read rules 1 and 4 twice. Rule 1 is the trap you have already met by hand. Rule 4 decides whether the output is usable at all: a model that quietly fills gaps produces a beautiful CSV you cannot check, and a model that marks ILLEGIBLE tells you exactly where to look.

Do not skip the three questions at the end. The row count is how you detect a dropped entry, and the ILLEGIBLE summary is a free map of where to spend your verification time.

Do this now Paste and run. If the upload stalls, check that you uploaded one roll and not the whole volume.
12

What should come back

Check these four things before you look at any row

  • Row count matches the entry numbers you can see in the PDF.
  • First and last row match the first and last entry on your pages.
  • The columns are the 21 asked for, in order, none invented.
  • Some cells say ILLEGIBLE. If none do, be suspicious, not pleased.

The last check is counter-intuitive enough to be worth stating twice. A perfectly clean CSV from a page whose margins are visibly wrecked means the gaps were filled, not read. Clean output is evidence of a problem here, not evidence of success.

13

Getting the file out intact

Ask for a file. If none comes, copy with your eyes open.

The prompt asks for a downloadable CSV. Amplify cannot make one — it does not run Python. Send the prompt anyway and read what comes back instead: how a tool behaves when it cannot do what you asked is part of what you are measuring.

  • If you get a file: download it, open it, read the first row and the last row.
  • If you get rows in the chat: the prompt told it to print CSV inside a code block. Copy from the code block. If it handed you a formatted table instead, ask again for the code block.

Four ways a copied table breaks

  • A comma inside a field pushes that row's columns one cell to the left. One row out of line, and nothing looks wrong.
  • Excel rewrites whatever it thinks it recognises — 3/1300 becomes a date, 04 becomes 4. The quietest of the four.
  • A markdown table lands in a single column, pipes and all, with |---| sitting in it as a data row.
  • The table stops early and whole rows never arrive. Count the rows.

Characters already damaged in the _verbatim columns take one more hit on every one of these routes.

Either route: check the row count, the first row, the last row, and every name against the page.

Be precise about the cause, because it changes what you should trust. Not one of those four is the model being wrong — its rows were fine, and the damage happened between the chat window and your spreadsheet. That is why the fix is the route and not a better prompt: a downloaded file avoids the whole class of problem, a code block avoids most of it, a formatted table avoids none of it.

The Excel one deserves a second look, because it is the only one that leaves no trace. A date silently rewritten is indistinguishable from a date you coded that way, and it survives every check except comparing against the page. If inquest_date comes back tidier than you left it, something edited it.

Write down what your tool actually did with the file instruction. Did it tell you it could not make one, or did it quietly hand you a table as though that were what you asked for? Substituting one format for another without saying so is the same habit as filling in a ward name you could not read. You will meet it again on slide 15 as a quiet error, and it is worth writing down while you are there.

14

How to line them up

Side by side, field by field, by case number

  • Open both CSVs in one spreadsheet, your rows above, the machine's below.
  • Sort both by case_number. Do not sort by anything else.
  • Go down a column, not across a row. You are comparing fields, not entries.
  • Note every disagreement as you go. Do not fix anything yet.

Comparing down a column rather than across a row is a small change with a large effect. It keeps one kind of judgement in mind at a time, so patterns appear — it gets the ward wrong whenever the margin is damaged — which never surfaces when you read across a row and meet twenty unrelated fields at once.

"Do not fix anything yet" matters because the disagreement rate is itself your result. If you silently correct as you go, you have destroyed your own measurement.

The point of the notes is that you see for yourself how often the machine is wrong, and where. Keep them in whatever form you will actually use while the two files are open in front of you.

15

Four kinds of disagreement

Label every disagreement as one of these

LabelWhat it looks like
LoudThe output is visibly broken — ^^''^^^, Crupiil^^aie, a number where a name should be.
QuietFluent, plausible, and wrong. A real ward name in the right slot — just not the one on the page.
Rule gapYou and the machine both defensible. The codebook did not say.
YouYou were wrong.

Most of your time goes on quiet, because it is the category you will find nothing in unless you go hunting. Loud errors announce themselves. Quiet ones look exactly like correct answers, and the only way to find them is to have the page open next to the row.

Here is the shape of one. The transcription says St. Mary atte Naxe. There is a real London church called St Mary Axe, and a model under pressure produces the real one: the right kind of word, in the right place, and not what the page says.

A high count of rule gaps is a good outcome, not a messy one. Those are the amendments that improve the codebook for everyone.

16

Upload and ask

Your CSV, not the machine's

  • Upload your own verified CSV — not the machine's output. Yours is a few kilobytes, well inside any upload limit.
  • Ask for the chart and the numbers behind it, in the same message.
  • Check the numbers against your spreadsheet before you keep the picture.
  • Gemini can create a chart using Python — it counts your rows, then renders them. Amplify "draws" a chart, like Firefly — it cannot run Python, so whatever comes back was generated, not counted.

The figure is built on your verified rows, not the machine's raw output. Otherwise the whole comparison gets quietly undone at the last step, and you end up charting the errors you just spent twenty minutes finding.

17

The chart prompt

Name the column. Ask for the table. Say n.

Chart prompt 1 — with your CSV attached
The attached CSV is my own hand-verified coding of Roll {{ROLL_LETTER}} of the London coroners' rolls, [ ] rows.

Count the values in the column `manner_of_death` and show me the counts as a plain table. Do not chart anything yet.
Chart prompt 2 — when the counts come back
Tell me if any rows were excluded from that count and why.
Chart prompt 3 — once the counts match your own
Make a single horizontal bar chart of those counts, with:
- categories sorted from most to least frequent
- the count printed at the end of each bar
- the title: "Manner of death, Roll {{ROLL_LETTER}} (n = [ ])"
- no 3D, no gradient, no drop shadow, no pie chart
- one colour for all bars, since the categories are not ranked

Send them one at a time and read each answer before the next. The order is the whole point: counts first, picture last. A chart is a claim about numbers, and once it is a picture nobody checks the numbers again. Asking for the table first makes the claim inspectable while it is still text — and sending the third message is how you confirm the counts, so check them against your own before you do.

The second message catches a real failure. Tools silently drop blank cells and rows they cannot parse, so a chart of 34 rows from a 39-row file is a different finding from the one you think you are reporting.

Swap manner_of_death for whichever column suits your question — weapon, perpetrator_outcome, ward. Same structure every time.

18

Two routes to a .docx

Either works. Both take under a minute.

  • Route A — ask the tool. Say "Put this into a Word document I can download" and take the .docx.
  • Route B — Google Docs. Paste your text in, then File → Download → Microsoft Word (.docx).

The chart: download it as an image, then Insert → Picture. Caption it with the field, the roll and the n.

Use Route B for anything with a chart in it. Route A is faster, but it re-flows the layout and sometimes drops an image; Google Docs lets you see the document before it becomes a file.

One rule on captions, and it is a research habit rather than a formatting rule: the caption must name the field, the roll and the n. A figure that does not say what it counted, or how many, is not evidence of anything.

If you only remember one thing. The machine is fastest exactly where the source is hardest — the margins, the footnotes, the numerals, the money — and it does not slow down or hedge when it reaches them. Your job is not to trust it or to refuse it. Your job is to know where it is weak and go look there.
